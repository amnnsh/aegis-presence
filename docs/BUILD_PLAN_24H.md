# The next 24 hours: prioritize evidence, not more screens

**Starting point:** the delivered frontend is the baseline. This plan describes proposed next work, not capabilities already built. One release owner coordinates three parallel contributors: backend/API, local models/liveness, and UX/QA. The time blocks below are elapsed wall-clock blocks totaling exactly 24 hours; owners can pair within a block.

**Non-negotiables:** no invented benchmark, no uploaded biometric footage without a separate explicit product/privacy decision, no client-only authorization, no inaccessible task as the only recovery path, and no unlabeled fallback. A failed integration remains unavailable; a stub never silently becomes a pass.

## Minimal backend contract, not implemented in this prototype

`POST /sessions` would create an expiring, tenant-bound challenge; `POST /sessions/{id}/evidence` would accept a schema-validated report with its untrusted provenance; `GET /sessions/{id}` would return a versioned policy outcome; `DELETE /sessions/{id}` would cancel and expire evidence. Backend authentication, consent, retention, replay policy, and origin controls need an explicit threat model. A server can enforce freshness and tenant boundaries, but cannot magically authenticate arbitrary JavaScript-generated camera scores.

For recovery, a passkey step-up may authenticate possession of a credential bound to the relying party. It must not be described as proof of a particular physical person's identity or current liveness. Document review and human escalation remain separate product decisions.

## Definition of an honest finish

At hour 24, every released signal says **observed**, **heuristic**, **experimental**, **simulated**, or **unavailable**. Tests demonstrate behavior rather than slogans. New backend storage is described accurately, and the no-biometric-upload promise still matches the architecture. Anything not completed is visible in the UI and README, not hidden inside a confident risk number.
